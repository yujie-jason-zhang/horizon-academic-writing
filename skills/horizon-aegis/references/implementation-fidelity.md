# Implementation Fidelity Audit (Step 5, conditional)

Run only when implementation artifacts are available under `AUTO`, or when the user selects `ON`.

**Not the goal:** code style, software engineering quality, elegance, test coverage.
**The goal:** determine whether the implementation that can generate the reported results is faithful to the manuscript's scientific description.

Trace one chain:

> **Claim → manuscript specification → implemented mechanism → result-generating execution path → reported evidence**

Use available read-only inspection tools. When repository history is needed to compare the released commit with the experiment version, inspect it with read-only commands such as `git log --oneline -20` and `git status` if the environment permits. Request that output from the user only when direct inspection is unavailable. Inspect project code and configurations without executing experiment scripts or modifying artifacts.

## 5.1 Algorithm Fidelity

Are equations, objectives, update rules, gates, state machines, thresholds, normalization, coordinate transforms, loss functions, operation ordering, and termination conditions implemented as described?

## 5.2 Hidden Mechanism Audit

Scientifically relevant behavior that affects results but is undisclosed or materially under-described in the manuscript:

- fallback logic
- hidden heuristics
- extra filtering or post-processing
- manual corrections
- privileged or ground-truth information
- undocumented initialization
- special-case rules
- auxiliary models or detectors
- environment-specific hard-coded logic

If an undeclared mechanism plausibly explains the claimed improvement, this is an **attribution problem**, not a documentation problem. Grade it accordingly.

## 5.3 Experiment-Code Consistency

Does the result-generating setup match the manuscript in: dataset splits · sensor/modality inputs · preprocessing · initialization · parameters and configuration values · random seeds · checkpoints · simulation settings · evaluation metrics · stopping criteria · runtime timing boundaries · baseline configuration?

Config files are a high-yield target: search the repo for each hyperparameter the paper states and compare.

## 5.4 Baseline Implementation Fairness

Do the proposed method and the baselines receive comparable treatment in compute, hardware, tuning effort, preprocessing, initialization, information access, priors, temporal smoothing, and evaluation settings?

A comparison is not scientifically fair if implementation asymmetry alone can explain the gain. Common asymmetries: the proposed method gets a tuned learning-rate schedule and the baseline gets defaults; the baseline is a reimplementation while the proposed method is the authors' optimized version; the baseline runs without the shared preprocessing the proposed method enjoys.

## 5.5 Result-Generating Path Audit

Verify that the claimed novel component actually participates in the execution path producing the reported results. Look for:

- novelty modules defined but never called
- disabled flags or default-off configurations
- stale checkpoints or old experiment scripts
- fallback branches that always dominate
- ablation branches accidentally used for final results
- repository state differing from the experiment version
- reported metrics generated by a different code path than the claimed method

When the claimed novel component exists in the manuscript or codebase but does not materially participate in the result-generating path, label it:

> **Dead Novelty** — normally **S4** when it affects the central contribution.

## Common AI-Coding Failure Patterns

- equation-to-code translation errors
- matrix multiplication order and inverse-transform mistakes
- coordinate-frame convention drift
- degree / radian mismatches
- sign errors
- missing normalization
- `<` versus `<=`
- Top-K sorting direction
- indexing shifts (off-by-one, 0- vs 1-based)
- inconsistent thresholds or defaults between config and code
- train / eval mode errors
- future-information leakage in supposedly online methods
- ground-truth leakage
- hidden fallback behavior
- stale configuration
- unused novelty modules
- comments or docstrings that no longer match executed behavior

## Status

- **Aligned** — the checked implementation materially matches the manuscript and result path.
- **Partially aligned** — local discrepancies, core scientific mechanism still faithful.
- **Unclear** — artifacts exist but do not determine the answer.
- **Partially verifiable** — supplied artifacts allow only part of the chain to be checked. **Name the missing artifacts** that block full verification.
- **Contradicted** — a material mismatch changes the method, information access, fairness, mechanism, or result interpretation.

## Severity mapping

| Finding | Typical level |
|---|---|
| Naming / notation mismatch, identical behavior | S1 |
| Local parameter discrepancy, little effect on conclusions | S2 |
| Undisclosed preprocessing, thresholding, or evaluation behavior affecting an important result | S3 |
| Materially unfair baseline implementation | S3-S4 |
| Core algorithm logic differs from the manuscript | S4 |
| Undeclared oracle / ground-truth information used by the method | S4 |
| Claimed novel module absent from the result-generating path (**Dead Novelty**) | S4 |

## The rule that overrides all of the above

> **No implementation supplied ≠ implementation mismatch.**

Never assign a severity level because artifacts were not provided to you. That belongs in `Not checked`, with the missing artifacts named.
